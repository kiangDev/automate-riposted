mini EDR บน macOS ที่ระดับ system call

ข้อเสนอโปรเจกต์จบ / ฝึกงาน · เขียนด้วย Zig + arm64 assembly · โฟกัส file & persistence telemetry · ระยะเวลา 24 สัปดาห์ · ผู้เสนอ: kiang

1ปัญหา

  • EDR บน macOS เป็นกล่องดำ — เมื่อเกิด incident ทีม security ตอบไม่ได้ว่า "ที่ log ไม่มี event นี้ เพราะไม่มีการโจมตี หรือเพราะ sensor มองไม่เห็น"
  • องค์ความรู้เรื่อง kernel ของ macOS มีน้อย — ตำรา OS สอน Linux เป็นหลัก ทั้งที่ XNU ต่างออกไปมาก (Mach + BSD, MACF, SIP, การยกเลิก kext) นักศึกษาที่อยากเข้าใจ kernel ของเครื่องที่ใช้อยู่ทุกวันแทบไม่มีจุดเริ่ม
  • ช่องว่างการมองเห็นในชั้น filesystem ของ APFS — syscall เฉพาะทางเช่น clonefile(2), fclonefileat(2), renameatx_np(2) คัดลอกและสลับไฟล์ได้โดยไม่ผ่านเส้นทาง open/write เดิม เครื่องมือ monitoring แต่ละชั้นเห็นไม่เท่ากัน แต่ยังไม่มีใครวัดออกมาเป็นตัวเลข

2ทำไมผมอยากทำ — ความรู้ที่ต้องการจากโปรเจกต์นี้

เป้าหมายไม่ใช่การสร้าง "อีกหนึ่ง security tool" แต่คือการเข้าใจเส้นทางที่คำสั่งหนึ่งคำสั่งเดินจากโปรแกรมลงไปถึง kernel แล้วกลับขึ้นมา ในระดับที่อธิบายได้ทุกขั้น การเขียน EDR บังคับให้ต้องรู้สี่เรื่องนี้โดยไม่มีทางเลี่ยง:

  • syscall ABI ระดับ instruction — บน arm64 การเรียก syscall คือ svc #0x80 โดยหมายเลขอยู่ใน x16 (บวก = BSD syscall, ลบ = Mach trap) argument อยู่ใน x0–x7
  • เส้นทางภายใน XNU — sysent table ที่ generate จาก bsd/kern/syscalls.master ต่อไปยังชั้น VFS
  • MACF (TrustedBSD MAC Framework) — จุดที่ Sandbox, AMFI และ EndpointSecurity เสียบตัวเองเข้าไปในเส้นทาง syscall นี่คือคำอธิบายว่า ทำไม EDR บน macOS เห็นบางอย่างและไม่เห็นบางอย่าง
  • ข้อจำกัดเชิงสถาปัตยกรรมของแพลตฟอร์มปิด — SIP, code signing, entitlement, การตายของ kext เป็นการตัดสินใจเชิงออกแบบที่มีเหตุผล การชนกับข้อจำกัดพวกนี้ด้วยมือตัวเองสอนเรื่อง OS security design ได้มากกว่าการอ่าน

ทักษะที่ติดตัวหลังจบ: อ่าน kernel source ของระบบปิดได้ · เขียนโค้ดที่คุยกับ kernel API ระดับ C ได้ · ออกแบบการทดลองเพื่อวัดขอบเขตความสามารถของเครื่องมือได้

3คำถามวิจัย

ชั้น monitoring ที่ใช้ได้จริงบน macOS สมัยใหม่ — FSEvents, kqueue/vnode และ EndpointSecurity — เห็น file operation ครบต่างกันแค่ไหน และมี syscall ใดที่หลุดจากการมองเห็นของแต่ละชั้น?

4สิ่งที่จะสร้าง

ส่วนประกอบรายละเอียด
SensorEndpointSecurity client เขียนด้วย Zig (@cImport เข้า header ภาษา C ตรง ๆ) subscribe event ตระกูลไฟล์: ES_EVENT_TYPE_NOTIFY_CREATE, _WRITE, _RENAME, _UNLINK, _CLONE, _EXEC
Persistence watcherเฝ้าจุดที่มัลแวร์ macOS ใช้ฝังตัวจริง — LaunchAgents/LaunchDaemons plist, login items, ~/Library/Preferences (macOS ไม่มี registry — ของเทียบเท่าคือชั้นนี้)
Rule engineกฎแบบประกาศ เทียบเคียงแนวคิด Sigma พร้อม process ancestry เพื่อลด false positive
asm coverage harnessโปรแกรม arm64 assembly ที่ยิง raw syscall ข้าม libc เพื่อทดสอบว่าแต่ละชั้น sensor ยังเห็นหรือไม่ ครอบคลุม syscall เฉพาะของ APFS
ผลการวัดcoverage matrix: syscall × ชั้น sensor × เห็น / ไม่เห็น / เห็นบางส่วน

ตัดออกอย่างตั้งใจ: network telemetry, การบล็อกแบบ AUTH event, central server หลายเครื่อง, การแจกจ่ายผ่าน MDM — เพื่อให้ 24 สัปดาห์ทำเสร็จได้จริงและลึกพอ

5ทำไม Zig และ assembly

Zig — เข้า C API ได้โดยไม่ต้องเขียน binding, ควบคุมการจัดสรรหน่วยความจำได้ชัดเจน (สำคัญมาก เพราะ ES handler ที่ช้าเกิน deadline จะถูก kernel ฆ่า client ทิ้ง), ไม่มี hidden control flow ให้เดา

Assembly — จำเป็นเพราะการทดสอบ coverage ต้องยิง syscall ที่ libc ไม่มี wrapper ให้ และต้องมั่นใจว่าไม่มีชั้นใดแทรกกลาง ส่วนนี้คือสิ่งที่เปลี่ยนโปรเจกต์จาก "เครื่องมือ" ให้เป็น "การวัดผล"

6ความเสี่ยงและแผนสำรอง

ขอ entitlement จาก Apple ไม่ผ่านใช้เครื่อง dev ที่ปิด SIP + amfi_get_out_of_my_way=1 ซึ่งเป็นวิธีมาตรฐานของงานวิจัยด้านนี้
ES client รันไม่ได้เลยดึง event ผ่าน /usr/bin/eslogger ของ Apple ได้ข้อมูลชุดเดียวกันโดยไม่ต้องมี entitlement
Zig ยังไม่นิ่งที่ API ระดับนี้ส่วนที่ติดกับ ES API เขียนเป็น C แล้วให้ Zig เรียก
